### #10 `fix(localmusic): ID3 标签 GBK 乱码识别与兜底解析` — ⚠️

作者 `shengxizi`，1 commit，2 文件（`.gitignore`、`LocalMusic.ets`）。

**做了什么**：`AVMetadata` 解出的标签可疑（含 U+FFFD，或 Latin-1 补充区字符过半且 ≥3 个）就置空，
交给已有的 ID3 解析 / 文件名兜底；`decodeId3Text` 的 `enc=0` 分支从"纯 Latin-1"改成
UTF-8 → GBK → Latin-1 三级尝试；`enc=1/2` 补 BOM 识别与 `utf-16be`。

**核实过的事实**
- `util.TextDecoder` **确实支持 `gbk` 与 `utf-16be`**（SDK `@ohos.util.d.ts` 的 encoding 列表）。
- `decodeText()` 内部是 `try/catch` 返回 `''`，所以 `gbk` 万一不被支持也只是静默退回 Latin-1，**不会抛**。
- 兜底链真实存在：`readMetadata` 里 `out.name.length === 0` → `parseId3FromFile` →
  `importOne` 里 `meta.name.length > 0 ? meta.name : titleFromFileName(label)`。置空是安全的。
- `looksGarbled` 的阈值（`high>=3 && high*2>=len`）对 "Björk Guðmundsdóttir" 这类欧洲名字不会误杀。

**要改**
1. **`enc=0` 的 GBK 分支有 Latin-1 回归**：判定条件是"GBK 结果无 U+FFFD **且含至少 1 个 CJK**"。
   `Björk` 的 Latin-1 字节 `B j F6 72 k`（`ö`+`r` 恰好组成合法 GBK 双字节）会被解成 1 个汉字而**被采纳**。
   建议改成比例判定：GBK 结果的 CJK 字数 ≥ 2 **或** 占非 ASCII 字符的 50% 以上。
2. **`.ape/.wma` 的兜底走不到**：`importOne` 第一句 `isSupportedAudioFile(label)` 按**扩展名**判，
   `.ape` 直接 `return 'unsupported'`，后面新增的 `detectAudioExtByContent` 永远执行不到。
   而 `DownloadService.buildFileName` 在 `quality === 'ape'` 时确实会写 `.ape`（下载要 ape 却回了 mp3 时中招）。
3. `.gitignore` 加 `dist/` 与本 PR 无关（scope creep），建议拆出。
4. 与 #13 **内容重叠**：#13 的补丁里包含本 PR 的全部改动。合了 #13 就等于合了 #10（见 §3）。

### #12 `fix(background): 长时任务被系统取消后自动补申请` — ⚠️（方向对，有两处硬问题）

作者 `shengxizi`，1 commit，2 文件（`BackgroundUtil.ets` **本地逐字节相同**、`MediaService.ets` 已分叉）。

**做了什么**
- `BackgroundUtil` 新增 `setTaskHoldPredicate()`（"现在还需不需要长时任务"）与 `lastContext`；
  `continuousTaskCancel` 回调里若"应用仍想要 + 仍需要"就自动补申请，上限 3 次。
- `MediaService` 注入判定 `() => isActuallyPlaying() || pausedByInterrupt`；
  `paused` 事件在 `kernelOwns` / `pausedByInterrupt` 时不再 `stopContinuousTask`；
  `stopped` 事件在 `kernelOwns` 时不再停任务；`onApplicationBackground/Foreground` 用 `|| isActuallyPlaying()` 兜底；
  **焦点中断先立 `pausedByInterrupt` 标志、再 `pause()`**（消除"paused 事件先到"的竞态）。

后半段（竞态修复、`kernelOwns` 不停任务）**判断准确、改动克制**，`paused`/`stopped`/`pause()`
三处都核过作用域（`kernelOwns` 是 `onStateChange` 里的局部变量，`pausedByInterrupt` 在 `pause()`/`pauseCall()`/
`INTERRUPT_HINT_STOP`/`RESUME` 四处清掉），语义自洽。

**必须改**
1. **取消原因映射写错了**。官方 `ContinuousTaskCancelReason`（SDK 与在线文档一致）：
   `1 = USER_CANCEL 用户取消`、`2 = SYSTEM_CANCEL 系统取消`、`3 = USER_CANCEL_REMOVE_NOTIFICATION`（**预留、暂未启用**）。
   PR 注释写的是"1=已取消/完成，2=后台负载过高，3=用户移除通知"，三条都不对。
2. **不能对 `USER_CANCEL(1)` 补申请**。那是用户在通知栏主动取消，立刻重新申请等于跟用户对着干；
   系统侧也有"非法使用后台任务"（`SYSTEM_CANCEL_USE_ILLEGALLY=11`）这类处置。
   必须收紧成 `reason === backgroundTaskManager.ContinuousTaskCancelReason.SYSTEM_CANCEL`。
3. **上限 3 次是无效的**：`systemCancelRequeues` 在每次 `startBackgroundRunning` 成功时清零
   （`BackgroundUtil.reconcile` 里 `systemCancelRequeues = 0`），而"起来 → 系统又取消"正是要防的场景，
   计数永远回 0 ⇒ 实际上是个**无上限、无间隔**的重试环。而且 `enqueue()` 是立刻执行，**没有任何退避**。
   建议：改成时间窗限流（60s 内最多 3 次）+ 补申请前 `setTimeout` 1~2s + 仅在任务**存活 ≥30s** 后才清零计数。

**建议补**
4. 官方还有 `on('continuousTaskSuspend')`（API 20+）：对"申请了 AUDIO_PLAYBACK 却没在播放"的长时任务，
   系统先**暂停**（退后台挂起、回前台自动激活），连续检测失败才取消（`detailedReason 6`）。
   建议一并注册做取证，避免"为什么后台还是断"再次无处查。
5. "永久失焦"没有看门狗：`pausedByInterrupt` 若一直等不到 `RESUME`，任务会被**无限期**持有。
   建议 60s 超时后清标志并停任务。

### #13 `fix(download): 下载与导入按实际内容修正扩展名` — ⚠️（含 #10）

作者 `shengxizi`，1 commit，3 文件。

**做了什么**（三条独立的修正，判断都准）
1. `FallbackOptions` 新增 `preferredQuality`，`resolveMusicUrlWithFallback` 用它取代"播放偏好"当首选档位
   —— 修的是"下载弹层选了 FLAC、播放偏好是 128k ⇒ 实际下到 128k，文件名却叫 `.flac`"。
   `options?` 仍是可选参数，**向后兼容**，这点很好。
2. 拿到 url 后 `task.quality = dlOutcome.quality`，再用 `buildFileName(name, singer, task.quality)` **重建文件名**
   —— 扩展名与音质标签都跟着实际档位走。顺序正确（赋值在 `buildFileName` 之前）。
3. 下载完按**容器头**再修正一次扩展名（`correctFileExtByContent`）。

**核实过**
- `writeAudioMetadata` 来自 `@dabing/taglib_harmony`，TagLib 是**按内容嗅探**的，临时文件名是 `dl_*.tmp` 也照样写，
  所以"改扩展名"不会让元信息写错格式、也不会腐蚀文件。这点 PR 里没写，值得补一句。
- `buildFileName` 的映射：`flac/flac24bit/hires/atmos/atmos_plus/master → .flac`、`ape → .ape`、`wav → .wav`、其余 `.mp3`。

**要改**
1. `DownloadService.detectAudioExt` **不跳 ID3v2 前置标签**（`fLaC` 前面挂 `ID3`），会把带 ID3 的 FLAC 误判成 `.mp3`；
   而同 PR 的 `LocalMusic.detectAudioExtByContent` **跳了**。同一件事两份实现、行为不一致。
   建议收敛成 `musicbasic` 里的一份，两处共用。
2. 同上 WAV 判定不一致：LocalMusic 版只校验 `WA`，DownloadService 版校验 `WAVE`。
3. `.ape/.wma` 的导入兜底仍走不到（同 #10 的第 2 点）。
4. **与 #10 重叠**：本 PR 的 `LocalMusic.ets` 补丁已包含 #10 的全部内容。

## 3. PR 之间的关系（合之前必须知道）

- **#10 ⊂ #13（严格子集，已逐行核对）**：`#13` 的 `LocalMusic.ets` 补丁新增 166 行、`#10` 新增 82 行，
  `#10` 的 82 行**全部**出现在 `#13` 里，`#13` 多出来的是 `detectAudioExtByContent` 与 `importOne` 的嗅探兜底。
  ⇒ 合了 #13 就等于合了 #10，`#10` 应标记 superseded 或直接关掉。
- **#11 / #12 / #14 逐个 hunk 重叠**（不是子集关系，是从同一份工作区分切出来的）：
  - `#11` = `MediaService` 的注释改写 + `TopAreaComponent` 删胶囊 + `SettingsDetailPage` 删按钮/改提示；
  - `#12` = `MediaService` 里 `#11` 的**那一段注释改写**（不含另外两个文件）+ 长时任务新逻辑；
  - `#14` = `SettingsDetailPage` 里 `#11` 的**那两段**（删按钮 + 改提示）+ 主题面板避让。
  三处重叠内容**逐字相同**，git 三方合并一般能自动消解，但顺序不同结果不同（见下面的合并顺序）。
- 换句话说：**这 7 个 PR 不是 7 条独立分支，而是从同一份本地工作区切出来的**，重复内容不少。
  真正"干净"的只有 #15（8 行、单文件）和 #16（9 文件、7 个逐字节相同）。

**推荐合并顺序**

```
#16  (9 文件、7 个逐字节相同、风险最低)
#15  (8 行)
#12  (先修 1/2/3 三个问题，再合)
#10 → #13  (先 #10 再 #13，或只合 #13 并把 #10 关掉标记 superseded)
#11 → #14  (#14 含 #11 的内容)
```
