## 3. QQ 扫码「不受信任的连接地址」
子任务交付（唯一文件 `features/player/src/main/ets/account/providers/TxProvider.ets`）：
- 根因（已确证）：校验点只有一处，校验的是 **MQTT broker 的 wss 连接地址**；旧代码把 `wss://${serverReference}/ws/handshake` 硬套 `^wss://([a-zA-Z0-9-]+\.)*y\.qq\.com(?::443)?/`，而 MQTT 5 的 Server Reference（CONNACK/DISCONNECT 0x9C/0x9D）**格式规范未规定**，真实返回多半是节点名/非 443/无路径等形态 ⇒ 必然误判。这是上一轮「用 reference 拼 endpoint + 写死白名单」引入的回归（备份里旧版根本不设 `options.endpoint`）。
- 改法：新增 `QR_BROKER_HOST/PORT/PATH`、`QR_TRUSTED_DOMAINS=['qq.com','tencentmusic.com','tencent.com']` 与 `resolveQrBrokerEndpoint()`；①官方域名族 → 用它给的 host/port/path（端口不限 443）；②单标签节点名 → 只拼到官方入口 `/ws/handshake/<节点名>`（host 仍是 `mu.y.qq.com`，票据不外流）；③IP/localhost/内网/userinfo 混淆/非 ws(s)/端口非法/非官方域名 → 拒绝。`options.endpoint` 全文件仅一处写入，首次连接/156-157 重定向/重连/CONNACK 采纳全部走同一判定。
- 日志：`RzdTxLogin`（每次连接前打 `raw=… -> endpoint=… source=… trusted=…`，拒绝时打 `actual=… expected=…`）。真实返回形态只能靠真机日志确证，若仍失败请回传 `被拒绝 actual=…` 整行。

### 2) QQ 扫码「不受信任的连接地址」间歇性失败
根因：那个校验现在只在**地址判定不可信**时抛错，而服务端有时给地址、有时不给 —— 给了不认识的地址就失败，不给就走官方默认入口成功，于是「有时能出二维码、有时报错」。
改法（`TxProvider.ets`）：**不再因为地址不可信而让扫码失败**。MQTT 5 明确允许客户端忽略 Server Reference；现在忽略它、回到我们自己的官方入口 `wss://mu.y.qq.com:443/ws/handshake`，只打日志（`RzdTxLogin`，`source=official-fallback`）。CONNACK 的 156/157 重定向若给了不可信地址，也一样忽略并回官方入口重试（最多 3 次），不再抛「不受信任」。
安全底线不变：**永远不会连到非官方域名/IP/内网地址**，票据只发官方域。

### 4) 概率性「扫码服务拒绝连接（reason 157）」——19:04 修正
157 = MQTT 5 的 0x9D「服务端已迁移」，服务端会同时给一个新地址。上一版把「不在官方域名族内」的地址**忽略**掉、回官方入口重试，于是服务端一直说"已迁移"、我们一直敲老地址 ⇒ 157 反复出现（概率性，因为服务端有时不给重定向）。
现在按 MQTT 5 的服务端重定向语义：**服务端让去哪就去哪**，只排除「明显不可能是 broker」的目标：
- 排除：非 ws(s)/http(s) 协议、含 `@`/反斜杠、缺 host、端口非法、本机/回环/链路本地/内网段（`localhost`、`.local/.internal/.lan`、`127.`、`169.254.`、`10.`、`192.168.`、`172.16-31.`、`::1`、`fe80::`）。
- 照用：官方域名族、公网 IP、任意域名、带/不带路径与端口、URL 编码、多候选（取第一个）。
- 单标签节点名仍拼到官方入口路径上；真排除时仍回退官方入口（不再抛错给用户）。
日志 `RzdTxLogin`：`source=reference-host | reference-path | reference-honored | default | official-fallback`。
产物核查：两包 `reference-honored` / `official-fallback` 为真；`扫码服务返回不受信任的连接地址` 为假。

### 7.1 本地实测（真值，`tools/qq-qr-probe*.mjs`）
| 探测 | 结果 |
| --- | --- |
| `CreateQRCode`（musicu.fcg） | HTTP 200、code=0，返回 `qrcodeID`/`qrcode`(png base64)/`expiresIn=900`；`webConf` 只是文案，`queryKey` 为空 |
| 轮询类方法 `CheckQRCode/QueryQRCode/GetQRCodeState/CheckLoginState` | 全部 `req_0.code=40000`（方法不存在）⇒ 没有 HTTP 轮询后路 |
| `wss://mu.y.qq.com:443/ws/handshake` × 12 次 | **157（0x9D 服务端已迁移）10 次 / reason=0 仅 2 次**（另有 8 次全 157、首轮 1/2 接受） |
| 157 的 Server Reference | 恒为 `11.168.22.98:29001` / `11.181.95.212:29001` 这类 **IP:29001**；CONNACK user 属性另给 `server=<IP>_29001` |
| 拿 wss 连 `IP:29001`（及 `IP:443` 各种路径） | 全部超时/失败（本机 TCP 到该 IP 的 443/29001 都被过滤）——**真机同样是「连接扫码服务失败：」** |
| 157 后在同一条连接上继续 SUBSCRIBE | 服务端直接断开 ⇒ 157 就是「走开，用别的服务器」 |

结论：**29001 是原生 MQTT/TCP 节点端口**，WebSocket 客户端跟不过去；官方 WS 网关本身是概率可用的（≈17%/次）。

### 7.2 改法
- `resolveQrBrokerEndpoint()`：非官方 host 的 reference，只有在「端口是 443/8443 或没写端口」这种**看着像 WebSocket 端点**时才照用；像 `IP:29001` 这种原生端口一律判为不可用 ⇒ 上层忽略它、重连官方入口。
- `connectQrMqtt()`：156/157 时忽略地址并**重试官方入口**（`QR_MAX_REDIRECTS=6` 次，间隔 300ms）——每次都是新连接，有机会落到不迁移的网关（≈17%/次 → 6 次约 90%）；重试完仍失败时给一句人话「扫码服务暂时不可用，请稍后重试」（细节全在 `RzdTxLogin` 日志）。
- `MqttUtil`：`连接扫码服务失败：` 后面**补上实际端点**（之前 err.message 为空时就是空白，用户看到的就是这个）。
- ⚠️ 结构性限制（已如实告知用户）：要做到 100% 稳，需要给扫码链路加**原生 TCP/TLS MQTT 传输**去连 reference 的 29001（真实客户端就是这么连的），那是独立改造。
