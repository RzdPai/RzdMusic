# 播放器动画/结构：现状、证据与重构方案（2026-11-17）

> 面向决策，不面向实现细节。实现细节见 `播放器关闭动画-日志分析-20261117.md`。

---

## 一、已经确证的事（有证据）

| # | 事实 | 证据来源 |
| --- | --- | --- |
| 1 | 关闭动画只有两条路：**② 反形变**（不 pop）/ **③ 根节点快照 + 壳层收缩后 pop** | 1.3.3 反汇编 `PlayerPage.closeWithAnimation` |
| 2 | 无界的快照回调**用 `err` 判失败**（`if (!err) 成功 else 直接 pop`），我们 10-22 改成了"只看 pixmap" | 同上，`&…&.#~@0>@1*#` |
| 3 | 用户复现的回调是 `err` 空壳（`code/message` 都是 undefined）+ `pix=1` ⇒ **无界判失败、我们判成功** | 用户 11:25:47 日志 |
| 4 | 无界关闭起手先 `dropWideImm()`（清宽屏沉浸态 `wideImm`/`wideImmT`），**我们没有这一步** | 1.3.3 `dropWideImm` 反汇编 |
| 5 | 我们的 `shrink START` 时 `pix=0`，`FINISH` 时才 `pix=1` ⇒ 补间前半段收缩层是空的 | 用户日志 |
| 6 | 1.3.3 的 `MainPage.startShrinkBack` 与我们的壳层补间同构（存 pixmap → `shrink.start`） | 1.3.3 反汇编 |

**结论**：不是"无界换了一套架构"，而是**同一套架构里几个判据/步骤不同**。
我们的问题集中在「什么时候认为快照可用」和「宽屏态收尾」这两处。

## 二、两个症状的归因（按可信度排序）

### 症状 A：关闭时封面跟着播放器下滑，而不是飞回去

| 置信度 | 原因 | 状态 |
| --- | --- | --- |
| 高 | 判据与无界相反 ⇒ 用了一张"空壳 err 的图"当成功；这张图若为空白/半帧，收缩层看起来就是"没有封面"，真页面随导航退场下滑 | **已修**（`c2a507d`，与无界对齐） |
| 中 | `shrink START` 时 `pix=0`（图晚于补间就位），补间前半段画空层 | 判据对齐后应消失；若仍出现，再改成**先等图再起补间** |
| 低 | 壳层 60ms 兜底先于快照回调启动补间 | 同上，判据对齐后这条更难触发 |

### 症状 B：展开播放器动画没有背景

| 置信度 | 原因 | 状态 |
| --- | --- | --- |
| 中高 | 上一次关闭把状态留在异常组合（`snapOwned=1` + `coverHidden=1`），下一次展开起手就处在"封面被压、背景层无图" | 部分：诊断已修对（`bdc709b`），根因待新日志确认 |
| 中 | 展开与关闭共用 `ExpandSnapshot` 共享状态，缺"关闭失败兜底"时的彻底复位 | 待确认 |

### 症状 C：宽屏 / 平板竖屏「两个封面」

| 置信度 | 原因 | 状态 |
| --- | --- | --- |
| 中 | 缺 `dropWideImm()` 这类宽屏态收尾（我们的等价物是 `isShortHeightWindow() && usePanelLayout()`，没有关闭期立即清态） | **未修**，需要宽屏日志确认 |
| 低 | `publishCoverHidden` 的消费端（我们注释里写着"本仓 flat 换面不做缩放，只算值不参与渲染"）与无界不一致 | 待评估 |

## 四、重构方案（两个选项）

### 选项 A：不动架构，继续按无界逐条对齐（**推荐先做**）

范围：
1. `dropWideImm` 等价物：关闭起手立即清宽屏态（约 20 行）。
2. 补间起手前确保图就位（若新日志仍显示 `pix=0`）。
3. 失败兜底走完时做一次**彻底复位**（`snapOwned/coverHidden/flatWide` 全清），避免污染下一次展开。

成本：1~2 天（含你复现验证 2 轮）。
风险：低。每步可单独回滚。

**为什么先做它**：目前所有证据都指向"判据/时序/收尾"三件小事，而不是"结构撑不住"。
无界 1.3.3 用的是**同一套** `componentSnapshot + onShrinkBack + 壳层补间`，而且它比 1.2.4
长大了近一倍（1351 vs 749 函数）却仍是这套结构 —— 说明这套结构本身能撑住。

### 选项 B：按 1.3.3 重写播放页（**不建议现在做**）

范围：以 1.3.3 的 `PlayerPage`（1351 函数）+ `MainPage` 的 morph 体系为蓝本重写我们的
`PlaybackPage.ets`（约 6 600 行，含大量历史注释与乱码注释）。

成本：**2~3 周**，且期间播放、歌词、锁屏、投屏、USB 输出全部要重测。
风险：高。1.3.3 是**混淆构建**，成员名是 `#~@0>@1*#`，只能靠"字符串常量 + 调试行号"逐函数还原，
**拿不到可编译的源码**；`PlayerPage` 里 1 351 个函数不可能全靠反汇编还原。

**结论**：B 不可行（不是"难"，是"信息不足"）。真要重构，也应该是**我们自己重写**，
口径以 A 的结论为准，而不是"照着反编译抄"。

## 五、建议的执行顺序

1. 你装 `298bf7b`，正常关闭 / 下拉关闭各几次，发日志 → 确认症状 A 是否已消失
2. 顺手抓一次宽屏/平板竖屏关闭日志 → 决定是否需要补 `dropWideImm` 等价物
3. 我按 1、2 的结论做选项 A 的剩余两项
4. 等 A 全部落地且真机稳定 3~5 天，再讨论"要不要大改结构"
