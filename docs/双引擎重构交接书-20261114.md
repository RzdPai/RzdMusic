**三条硬约束**（违反会直接导致线上事故）：

- **不要改 `LXPlayHelper` / `LXMusicSDK` 的调用签名。** 本次目标是把引擎换掉，不是把上层重写。

> 同理，「LX 一定不需要 DOM」也不成立：桥自身 0 次 DOM，但第三方脚本可能用 `document` 做 HTML 嗅探。**两个方向都不能预设。**

## 0.1 结论摘要（2026-11-14 修订，先读这一节）

**这版推翻了上一版的两条预设，接手时按本节为准。**

| 上一版 | 这一版（正确） |
|---|---|
| 「MusicFree 必须留 ArkWeb」 | **按脚本能力路由**：只有 `require('cheerio')` 的插件才需要 DOM，纯 API 插件不需要 |
| 「LX 一定走 QuickJS」 | 第三方 LX 脚本可能用 `document`，同样要探测 |
| 一上来就编 QuickJS | **先做 Phase 0.5（注入改造，1 天，不依赖 QuickJS），再做 QuickJS** |

**三条核心判断：**

1. **分界线是能力，不是品牌。** `probeScript()` 静态扫脚本 → `needsDom` 为真走 WebView，否则走 QuickJS。两边都不写死。
2. **注入慢的根因不需要 QuickJS 就能解决。** `onInterceptRequest` + `setResponseData(fd)` 把 114 次 `runJavaScript` 压成 1 次资源请求，体积从 base64 的 2.13MB 回到 1.6MB。这是全案唯一「零风险、收益确定」的改动。
3. **QuickJS 只值「内存」这一项，且必须实测。** 官方没有单个 ArkWeb 组件常驻内存的数字，「省 80MB」是假设，不是事实。

**两条砍线（任一成立就退回「只做 Phase 0.5」，删掉 native 代码）：**

- `hidumper` 实测 `(LX+MF 双 WebView) − (QuickJS)` 的内存差 **< 30MB**
- 真实用户脚本里 `needsDom = true` 的比例 **> 50%**

**工期**：Phase 0 + 0.5 = **1.5 天**（可独立交付）；全案 13.5 ~ 19.5 天。

**如果只做一件事**：做 Phase 0.5。它会同时给你两个数字——注入耗时降了多少、两个 WebView 到底占多少内存。第二个数字直接决定后面 12 天值不值得干。

## 1. 事实基线（2026-11-11 实测，不是猜的）

### 1.1 代码规模

| 指标 | 数值 |
|---|---|
| `.ets` 文件 | 373 个 |

| 第二大 | `common/musicbasic/src/main/ets/model/PlayerExpandState.ets` 6,709 行 |

### 1.2 音源引擎现状

**纯 ArkWeb，两个隐藏 WebView 常驻。**

| 引擎 | 宿主组件 | 载体 | 脚本载体 |
|---|---|---|---|
| LX（洛雪脚本） | `LXSourceHost` → `LXSourceEngine` | `Web({src:$rawfile('lx_bridge.html')})` | `lx_bridge.html` 33KB |
| MusicFree（插件） | `LXSourceHost` → `MusicFreeEngine` | `Web({src:$rawfile('mf_runtime.html')})` | `mf_env.js` 57KB |

- 常驻原因见 `LXSourceHost.ets:15-16`：WebView 一旦卸载，注入的插件状态全丢。
- **QuickJS 在整个仓库零痕迹**：文件名 0 个、内容 0 处、native 层只有 `cpp/mpv_bridge.cpp`、`oh-package.json5` 无相关依赖、`docs/` 50MB 文档里 0 处提及。**它不是被删的，是从来没落地。**

### 1.3 为什么可以切分（关键证据）

| 维度 | LX 脚本侧 | MusicFree 插件侧 |
|---|---|---|
| `document.` 出现次数 | **0**（`lx_bridge.html` 全文） | `mf_env.js` 里有：`document.createElement('div')` + `innerHTML` + `querySelectorAll`（1489/1499/1507），**但只在 `require('cheerio')` 时走到** |
| 网络 | 全走 `window.lx.request` → `ohos_bridge` → **原生 http** | axios 也走原生桥 |
| 依赖的宿主 API | `window` / `atob` / `btoa` / `TextDecoder` / `escape` / `setTimeout` / `Promise` | HTML DOM（**仅 cheerio 路径**） |

**结论（修正版，2026-11-14）**：分界线不是「LX vs MF」，而是「脚本运行时是否需要 DOM」。

| 事实 | 含义 |
|---|---|
| LX 桥自身 `document.` = 0 | 桥不需要 DOM，但**第三方 LX 脚本可能用**（HTML 嗅探类脚本无法穷举） |
| `mf_env.js:1548` 的 `'cheerio': { load: cheerioLoad }` 是**模块表里的按需项** | 只有 `require('cheerio')` 的插件才建 DOM；纯 JSON API 插件不需要 |
| `mf_env.js` 的 axios 走原生桥 | 网络层面两边等价，不构成差异 |

所以「MF 必须留 WebView」「LX 一定走 QuickJS」**两个方向都是过强断言**。正确形态是**运行时按脚本能力路由**（见 2.0），引擎是探测结果，不是配置项。

### 1.4 当前方案的实测代价

`LXSourceEngine.ets:398-415`（`injectScript`）：

```ts
const b64: string = this.toBase64(initDataJson);   // base64 使体积 +33%
const partSize: number = 20000;
codes.push(`window._lx_init_begin(${gen});`);
for (let i = 0; i < b64.length; i += partSize) {
  codes.push(`window._lx_init_chunk(${gen}, '${b64.substring(i, i + partSize)}');`);
}
codes.push(`window._lx_init_end(${gen});`);
appendLog('引擎 注入分片数=' + (codes.length - 2) + ' gen=' + gen);
```

1.6MB 脚本 → base64 约 2.13MB → **约 112 片**（真机日志实测 `注入分片数=114`），每片一次跨 ArkTS↔WebView 的 `runJavaScript`，且 `runJsSequential` 是串行 Promise 链。这是冷启动卡顿的确定来源之一（日志关键字：`注入分片数=`）。

## 2. 目标架构

### 2.0 先定路由规则（不绑定品牌）

```
     脚本（LX 订阅 / MF 插件）
            │
            ▼
   probeScript(script) → { needsDom, needsWebCrypto, needsCompression }
            │
     needsDom ─┬─ true  ──▶ WebViewRuntime（ArkWeb，能力全集）
               └─ false ──▶ QuickRuntime（QuickJS，缺能力自动回退 WebView）
```

| 探测项 | 判定依据（**静态扫描文本，不执行**） | 路由 |
|---|---|---|
| `needsDom` | 含 `document.` / `DOMParser` / `innerHTML` / `querySelector` / `require('cheerio')` / `require("cheerio")` | true → WebView |
| `needsWebCrypto` | 含 `crypto.subtle` | true → QuickRuntime 补齐则 QuickJS，未补齐则 WebView |
| `needsCompression` | 含 `DecompressionStream` / `CompressionStream` | 同上 |

**探测必须「宁可误判有、不可漏判无」**：判成需要 DOM 只是多占一个 WebView（功能正常），漏判会导致脚本直接 `ReferenceError`。所以规则要宽——文本里出现 `document` 这个词（哪怕在字符串常量里）就算命中。

**落地效果**：LX 脚本多数 → QuickJS；元力纯 API 插件多数 → QuickJS；用 cheerio 的插件、用 document 的脚本 → WebView。**没有任何一侧被写死**，未来新格式自动适配。

### 2.1 运行时组成

```
┌──────────────────────────── ArkTS ────────────────────────────┐
│  LXSourceHost（常驻宿主，对外接口不变）                        │
│    ├── SourceRuntime（统一接口：init / request / eval）         │
│    │     ├── LxQuickEngine     ← 新增：NAPI 调 liblxquick.so   │
│    │     └── LXSourceEngine    ← 保留：ArkWeb（逃生口）         │
│    └── MusicFreeEngine ← 按 probeScript 结果决定走哪个 Runtime  │
└───────────────────────────────────────────────────────────────┘
                    │ NAPI (同步/任务投递)
                    ▼
┌──────────────── libquickjs.so（新增 native 模块）─────────────┐
│  quickjs-ng 内核 + 定时器线程 + 消息桥                          │
│  运行 engine.js（由 lx_bridge.html 的 <script> 抽出来）         │
└───────────────────────────────────────────────────────────────┘
```

### 2.2 不变的部分（冻结，不要改）

- `LXPlayHelper.ets`、`LXMusicSDK.ets`、`MusicFreeAdapter.ets` 的全部调用签名。
- `LXSourceEngine.ets:8-11` 导出的三个模块级符号：

```ts
export let lxEngineSendRequest: ((key: string, data: LXSourceRequestData) => void) | null = null;
export let lxEngineRegisterPromise: ((key: string, resolve, reject) => void) | null = null;
export let lxEngineIsReady: boolean = false;
export async function waitForLxEngineReady(timeoutMs: number = 3000): Promise<boolean>;
```

新引擎必须继续导出这三个符号 + 一个函数，语义完全一致。这样 `LXPlayHelper` 一行不用改。

**注意**：这三个是 `export let` 模块级变量，由组件在挂载时赋值。切换开关时**必须保证同一时刻只有一个引擎在写**——`aboutToDisappear` 里要把它们置回 `null` / `false`，否则 WebView 引擎卸载后仍指向已销毁的实例，就会「假就绪 + 请求打到空气」。

### 2.3 需要新建的部分

| 新增物 | 路径 | 职责 |
|---|---|---|
| **脚本能力探测** | `features/player/src/main/ets/source/ScriptProbe.ets` | `probeScript(script): ScriptProfile`，纯字符串扫描，无副作用 |
| **运行时接口** | `features/player/src/main/ets/source/SourceRuntime.ets` | 统一 `init / request / cancel / isReady`，两个后端都实现它 |
| **注入改造** | `LXSourceEngine.ets` / `MusicFreeEngine.ets` | `runJavaScript` 分片 → `onInterceptRequest` + 文件句柄（见 Phase 0.5） |
| QuickJS 静态库 | `features/player/src/main/cpp/quickjs/`（vendored 源码） | quickjs-ng |
| NAPI 桥 | `features/player/src/main/cpp/lx_quick_bridge.cpp` | eval / 消息 / 定时器 |
| 引擎 JS | `features/player/src/main/resources/rawfile/lx_engine.js` | 由 `lx_bridge.html` 的 `<script>` 抽出，逻辑不改 |
| ArkTS 引擎组件 | `features/player/src/main/ets/source/LxQuickEngine.ets` | 实现 `SourceRuntime` |
| 引擎开关 | `MusicStoreService` 新增 `KEY_LX_ENGINE_MODE` | `'auto'` / `'webview'` / `'quickjs'`，默认 `auto`（按探测结果） |

`KEY_LX_ENGINE_MODE` 的 `'auto'` 是默认值，也是「不强制」的落点：用户不需要知道哪个源跑在哪个引擎上。

### 2.4 被否掉的方案（决策记录，不要重新发明）

| 方案 | 做法 | 为什么不选 |
|---|---|---|
| **A. 统一 QuickJS**（连 MF 也搬） | 给 QuickJS 塞一个最小 DOM（linkedom 类），让 cheerio 能跑 | `mf_env.js:1440` 依赖「cheerio 集合可迭代」+ 属性直读 + `querySelectorAll`，DOM 实现要覆盖 `createElement/innerHTML/属性/迭代器` 全套。工作量 ≥ 1 周，HTML 解析性能比原生 DOM 差一个数量级，且每个插件行为都要重新验证。 |
| **B. 统一 WebView**（不引入 QuickJS） | 只做 Phase 0.5 | **不是被否掉，是并列选项。** Phase 4 若实测内存差 < 30MB，B 就是最终答案，Phase 1~5 全部cancel。 |
| **C. 单 WebView + 双 iframe** | 一个 Web 组件里跑两个同源 iframe，各自独立 realm | 省的主要是进程开销（iframe 共享渲染进程，JS 堆仍两份）；桥要按来源分流，一个 iframe 崩了两个一起挂。成本 2~3 天，收益 < QuickJS，且完全没解决 crypto/压缩 的 native 化。 |
| **D. 嵌 Hermes / V8** | 复用 RN 生态的 JS 引擎 | Hermes **不支持 `eval` / `new Function`**（我们执行用户脚本就靠它），直接出局。V8 体积是 QuickJS 的 5~10 倍。 |
| **E. 多进程隔离**（每个脚本一个进程） | 用 ExtensionAbility 跑脚本 | 进程启动成本 100ms+，IPC 更重，与「省资源」目标相反。 |

**为什么是 QuickJS**：`quickjs-ng` 的 arm64 so 约 1MB；支持 `eval`；C API 极简，NAPI 绑定一天能写完；无外部依赖。四条件同时满足的引擎只有它。

**这个方案在什么情况下不成立**：① Phase 4 实测内存差 < 30MB；② 真实用户脚本里 DOM 依赖比例 > 50%（意味着 QuickJS 只能接管不到一半的脚本，native 成本摊不平）。两条任一成立，就退回方案 B。

## 3. 接口契约（最关键的章节，实现必须逐字对齐）

### 3.1 JS → Native：唯一出口

JS 侧只有一条通道，`lx_bridge.html:73-84`：

```js
window.ohos_bridge.onMessage(JSON.stringify(data))
```

`data.event` 取值与载荷（ArkTS 侧解析见 `LXSourceEngine.ets:642` `handleJsMessage`）：

| event | 载荷字段 | ArkTS 处理 |
|---|---|---|
| `nativeFetch` | `requestId:number, url, method, headers, body, timeout` | `handleNativeFetch()`：用 `@ohos.net.http` 发请求，再回调 JS |
| `init` | `status:boolean, message, sources, gen:number` | 写 `lxEngineIsReady`；`gen !== pageGen` 时**丢弃**；成功时 `saveApiSources()` |
| `response` | `requestKey:string, status:boolean, message, result` | 兑现/拒绝 `pendingRequests` |
| `updateAlert` | `log, updateUrl` | 写 AppStorage `lxUpdateAlertLog/Url/Version` |
| `log` | `message` | `appendPlayLog()` |

### 3.2 Native → JS：四个入口（名字不能变）

| 入口 | 签名 | 调用点 |
|---|---|---|
| `window._lx_init(gen, initData)` | 初始化脚本，`initData` 见下 | `_lx_init_end` 内部调用 |
| `window._lx_handleFetchResponse(requestId, errStr, status, headersJson, bodyText)` | 回填网络结果 | `handleNativeFetch` → `runJs` |
| `window._lx_handleRequest(reqKey, reqDataJson)` | 派发一次调用 | `lxEngineSendRequest` |
| `window._lx_init_begin/chunk/end` | 分片装配（**QuickJS 版可保留但不用**，见 5.3） | `injectScript` |

`initData` 字段（`lx_bridge.html:611` 起）：`name / description / version / author / homepage / script`。

### 3.3 一次调用的完整链路（用来验证移植是否等价）

```
ArkTS: lxEngineSendRequest(key, {source, action, info})
  → Native→JS: window._lx_handleRequest(key, json)
    → 脚本 handler
      → window.lx.request(url, opts, cb)
        → sendToNative({event:'nativeFetch', requestId, ...})
          → ArkTS: handleNativeFetch → http.createHttp
            → Native→JS: window._lx_handleFetchResponse(requestId, ...)
              → cb(null, resp)
    → sendToNative({event:'response', requestKey:key, status, result})
      → ArkTS: pendingRequests.get(key).resolve(result)
```

**移植验收标准**：这条链路上每一跳的日志都能在 `appendPlayLog` 里看到，且顺序与 WebView 版一致。

### 3.4 代际（gen）语义

- WebView 版：`pageGen` 在 `onPageEnd` 自增，注入时带上；桥和 ArkTS 两侧都按 gen 丢弃过期事件。
- QuickJS 版：**复用同一套语义**。每次重载脚本时 `gen++`，注入时带入，`init` 回来校验。
- 不要改成"单次消费"闩锁——旧实现就是永久闩锁，WebView 被系统回收后会假就绪。

## 4. 关键技术细节（不写清楚会卡住）

### 4.1 QuickJS 选型与编译

- 用 **quickjs-ng**（`https://github.com/quickjs-ng/quickjs`），不要用原版 `bellard/quickjs`（已停止维护）。
- 编译参数：

```cmake
set(CMAKE_CXX_STANDARD 17)
add_library(quickjs STATIC
    quickjs-ng/quickjs.c
    quickjs-ng/libregexp.c
    quickjs-ng/libunicode.c
    quickjs-ng/cutils.c
    quickjs-ng/quickjs-libc.c   # 只用它的 std/os 部分，或整个排除
)
target_compile_definitions(quickjs PRIVATE
    CONFIG_BIGNUM=1
    CONFIG_ATOMICS=0
)
```

- `abiFilters` 只有 `arm64-v8a`（与 `features/player/build-profile.json5:13` 一致）。
- **必须与 mpv 共用同一个 `libc++_shared.so`**，不要另编一份，否则打包冲突。

### 4.2 线程模型（最容易写错的地方）

QuickJS 的 `JSContext` **不是线程安全的**。方案：

- 起一条专属线程（`pthread`），线程内跑主循环：`JS_IsJobPending` → `JS_ExecutePendingJob` → 处理定时器队列 → 处理消息队列。
- ArkTS → JS 的调用（`runJs` / `sendRequest`）**只投递任务到队列**，不直接 `JS_Eval`。
- 所有 NAPI 方法都在 ArkTS 线程被调用，内部用 `napi_create_threadsafe_function` 或简单 mutex + 条件变量转交。
- 线程退出时先 `JS_FreeContext` 再 `JS_FreeRuntime`，且要等队列排空。

### 4.3 内存与栈

```c
JS_SetMemoryLimit(rt, 256 * 1024 * 1024);  // 256MB 上限，防止脚本泄漏拖死进程
JS_SetMaxStackSize(rt, 8 * 1024 * 1024);   // 8MB，脚本递归可能很深
JS_SetGCThreshold(rt, 4 * 1024 * 1024);
```

- 1.6MB 脚本 `JS_Eval` 实测约 80~150ms（解析+执行），远优于 105 次 `runJavaScript`。
- 每次请求结束调 `JS_RunGC(rt)` 有性能代价，改为**每 N 次或内存阈值触发**。

### 4.4 必须补齐的宿主能力（**本方案最大的工作量，不是"加几个 polyfill"**）

`lx_bridge.html` 的 `<script>` 是 840 行纯 JS（第 10~850 行），无 DOM 依赖，可整体搬。但它暴露给脚本的 `window.lx.utils` 有四个能力域直接建立在浏览器 API 上，QuickJS **一个都没有**：

| `lx.utils` 能力 | 桥内实现位置 | 依赖的 Web API | QuickJS 处置 |
|---|---|---|---|
| `crypto.md5` | 408~535 行，**纯 JS 自实现** | 无 | ✅ 直接搬，128 行照抄 |
| `crypto.aesEncrypt` | 513~525，`crypto.subtle` AES-CBC/ECB | **`crypto.subtle`** | ❌ 需补：vendored `tiny-AES-c` 或 mbedtls，NAPI 暴露 |
| `crypto.rsaEncrypt` | 527~534，`crypto.subtle` RSA-OAEP + SPKI 解析 | **`crypto.subtle`** | ❌ 需补：mbedtls RSA + SPKI/DER 解析，或纯 JS（~300 行） |
| `crypto.randomBytes` | 536~540，`crypto.getRandomValues` | **`crypto.getRandomValues`** | ❌ 需补：native `getrandom(2)` / `/dev/urandom` |
| `zlib.inflate` | 542~570，`DecompressionStream('deflate')` | **`DecompressionStream`** | ❌ 需补：vendored `miniz`（单文件 C，约 5k 行） |
| `zlib.deflate` | 572~600，`CompressionStream('deflate')` | **`CompressionStream`** | ❌ 同上 |
| `buffer.from` / `bufToString` | 325~407，纯 JS | 无 | ✅ 直接搬 |

**其余基础 API**（这些才是真正"写几十行 polyfill"的部分）：

| API | 用在哪 | 处置 |
|---|---|---|
| `atob` / `btoa` | `lx_bridge.html:111/288/298` | 纯 JS polyfill，约 20 行 |
| `escape` / `unescape` | `lx_bridge.html:111` 的 `decodeURIComponent(escape(atob(...)))` | **必须 polyfill**（`escape` 在 QuickJS 不存在），或把该行改成 `TextDecoder` |
| `TextEncoder` / `TextDecoder` | 318 / 322 / 424 | 纯 JS polyfill（UTF-8 编解码） |
| `setTimeout/clearTimeout/setInterval/clearInterval` | 脚本普遍使用 | native 定时器线程 + `JS_Call` |
| `console.log/warn/error` | 桥内大量 | 转 `sendToNative({event:'log'})` |
| `window` | 桥根对象 | `globalThis.window = globalThis` |
| `window.addEventListener('error'/'unhandledrejection')` | 823~832 | QuickJS 无事件模型：改为包住每次 eval 的 try/catch + `JS_SetHostPromiseRejectionTracker` |
| `document` | 桥自身不用，第三方脚本可能用 | 空壳对象，属性访问返回 `undefined` |
| `localStorage` | 部分脚本用来缓存 | 内存版 Map（不落盘），或空实现 |

**建议的 native 依赖策略**：`miniz`（zlib）+ `mbedtls`（AES/RSA/随机数），总体积约 300KB，全部同步接口，NAPI 直接暴露；JS 侧再包成 `crypto.subtle` 那种 Promise 形状。**不要尝试纯 JS 实现 deflate**——miniz 更可靠。

**决策点**：如果只想先跑通 5 个主力平台，可以先实现 `randomBytes + zlib`，把 `aesEncrypt/rsaEncrypt` 抛 `Error('需 WebView 模式')`，遇到调用该能力的脚本自动降级。**这个降级路径必须实现**，否则个别脚本会静默失败。

### Phase 0.5：注入改造（1 天，**不依赖 QuickJS，必须先做**）

**这一阶段解决什么**

现在 `injectScript()` 把脚本 base64（+33% 体积）后切成 112 片，逐片 `runJavaScript` 串行执行。这是冷启动卡顿的**确定来源**，且与用哪个引擎无关——WebView 路径同样受害。

**官方能力（已核实 SDK 声明）**

`@ohos.web.webview` / `component/web.d.ts`：

```ts
setResponseData(data: string | number | Resource | ArrayBuffer): void;
// number 类型 = file handle（文件句柄）
```

`onInterceptRequest` 支持通过**文件句柄**返回内容，一次性提供完整响应。配合 `WebResourceResponse.setResponseHeader` 加 `Access-Control-Allow-Origin`。

**顺带实现 `probeScript`（约 30 行，不依赖 QuickJS）**

Phase 4 的决策表需要真实分布数据，所以探测函数在 Phase 0.5 就要能跑（此时只打日志，不参与路由）。

```ts
export interface ScriptProfile {
  needsDom: boolean;
  needsWebCrypto: boolean;
  needsCompression: boolean;
}

const DOM_HINTS: string[] = ['document.', 'DOMParser', 'innerHTML', 'querySelector',
  "require('cheerio')", 'require("cheerio")', 'window.document'];
const CRYPTO_HINTS: string[] = ['crypto.subtle'];
const COMPRESS_HINTS: string[] = ['DecompressionStream', 'CompressionStream'];

export function probeScript(script: string): ScriptProfile {
  return {
    needsDom: DOM_HINTS.some((k: string) => script.includes(k)),
    needsWebCrypto: CRYPTO_HINTS.some((k: string) => script.includes(k)),
    needsCompression: COMPRESS_HINTS.some((k: string) => script.includes(k))
  };
}
```

**规则是「宁可误判有」**：`includes` 命中就算，不做语法分析。误判的代价是多挂一个 WebView（功能正常），漏判的代价是脚本直接 `ReferenceError`。

日志格式：`[RzdProbe] id=<apiId> dom=<0/1> crypto=<0/1> zlib=<0/1> size=<KB>`。运行一周后统计，就是 Phase 4 决策表的第二列。

**实现（四步）**

1. **脚本落到沙箱文件**（一次 IO，约几 ms）：

```ts
const path = `${context.cacheDir}/lx_engine_${gen}.js`;
const file = fs.openSync(path, fs.OpenMode.CREATE | fs.OpenMode.READ_WRITE | fs.OpenMode.TRUNC);
fs.writeSync(file.fd, script);      // 原始文本，不 base64
fs.closeSync(file.fd);
```

2. **Web 组件挂拦截**：

```ts
Web({ src: $rawfile('lx_bridge.html'), controller: this.controller })
  .onInterceptRequest((event) => {
    const url = event.request.getRequestUrl();
    if (!url.startsWith('https://lx.local/engine.js')) { return null; }
    // 不要用全局 URL 类：ArkTS 里它在 @ohos.url 模块下，不是全局对象
    const m = url.match(/[?&]gen=(\d+)/);
    const gen = m === null ? -1 : Number(m[1]);
    if (gen !== this.currentGen) { return null; }        // 代际过期：404，不返回旧脚本
    const resp = new WebResourceResponse();
    const f = fs.openSync(this.scriptPath(gen), fs.OpenMode.READ_ONLY);
    this.openFds.push(f.fd);                              // 统一管理，页面刷新前关闭
    resp.setResponseData(f.fd);
    resp.setResponseMimeType('text/javascript');
    resp.setResponseEncoding('utf-8');
    resp.setResponseCode(200);
    resp.setResponseHeader([{ headerKey: 'Access-Control-Allow-Origin', headerValue: '*' }]);
    return resp;
  })
```

3. **桥侧改为 `<script>` 标签加载**（不是 fetch + eval，省一次字符串复制）：

```js
const s = document.createElement('script');
s.src = 'https://lx.local/engine.js?gen=' + gen;
s.onload = () => { window._lx_init_done(gen); };
s.onerror = () => { window._lx_init_fail(gen, 'script load failed'); };
document.head.appendChild(s);
```

> 为什么用 `<script>` 而不是 `fetch().then(text => eval(text))`：`fetch` 要把 1.6MB 读成字符串再交给 `eval`，内存峰值翻倍；`<script>` 由引擎流式解析，峰值最低，且语法错误能被 `onerror` 捕获。
>
> `window.lx` 必须**先于**用户脚本就绪——bridge 自己的 `<script>` 在 `<head>`，天然满足。

4. **fd 生命周期**：`onInterceptRequest` 不保证框架何时读完。保守做法是把 fd 记进数组，在 `controller.refresh()` 之前、`aboutToDisappear()` 里统一 `fs.closeSync`。**不要**在返回响应后立刻关。

**收益（可量化）**

| 指标 | 现在 | 改造后 |
|---|---|---|
| 跨 ArkTS↔WebView 调用 | 114 次串行 `runJavaScript` | 1 次资源请求 |
| 传输体积 | base64 后 2.13MB | 原始 1.6MB |
| ArkTS 侧字符串峰值 | 2.13MB + 分片副本 | 0（只传 fd） |
| MF 引擎（`mf_env.js` 57KB） | 同样 base64 注入 | 同样适用 |

**验收**

- 日志不再出现 `注入分片数=`，改为 `injectMs=<数字>`，冷启动注入耗时下降 ≥ 60%。
- 6 平台脚本各注入一次成功；换脚本 10 次无残留（gen 递增，旧 URL 返回 404）。
- MF 插件搜索/取址无回归。

**回滚点**：`onInterceptRequest` 不生效时保留原 `injectScript` 作为 fallback（`KEY_LX_INJECT_MODE`：`'script-src'` / `'chunked'`）。

### Phase 3：移植桥 JS（4~6 天，**不是 2 天**）

工时之所以比直觉长，是因为 4.4 的加密/压缩能力要现补。

**做什么**

1. 从 `lx_bridge.html` 抽出 `<script>` 全部内容（第 10~850 行，840 行）→ `rawfile/lx_engine.js`。
2. **业务逻辑一行不改**，只替换环境适配层：
   - `window.ohos_bridge.onMessage(...)` → `native.sendToNative(...)`（NAPI 全局对象）
   - `window._lx_handleFetchResponse` / `window._lx_handleRequest` / `window._lx_init` → 保持同名，挂在 `globalThis`
   - `window._lx_init_begin/chunk/end` → 保留（QuickJS 不需要分片，但保留可让 diff 最小，也便于回退）
   - `window.addEventListener('error'/'unhandledrejection')` → 换成 eval 外包 try/catch + `JS_SetHostPromiseRejectionTracker`
3. 补 4.4 的六个能力（md5 直接搬，其余走 native）：
   - `miniz` → `zlib.inflate/deflate`
   - `mbedtls`（或 tiny-AES + 自写 RSA-OAEP）→ `aesEncrypt` / `rsaEncrypt` / `randomBytes`
   - JS 侧包成 Promise 形状，与 Web Crypto 签名一致（脚本是 `await lx.utils.crypto.aesEncrypt(...)`）
4. ArkTS 侧 `LxQuickEngine.ets` 照抄 `LXSourceEngine.ets` 的对外面：
   - 三个模块级导出 + `waitForLxEngineReady`
   - `initScript()` / `setReady()` / `handleJsMessage()` / `handleNativeFetch()` **抽到 `LxEngineCore.ets` 复用**（见下）
5. 注入改为 `JS_Eval` 一次完成，**不再 base64、不再分片**。

**必须知道的两个 eval 语义差异**

| | WebView 版 | QuickJS 版 |
|---|---|---|
| 桥与脚本的关系 | 脚本在桥的 IIFE 闭包内 `eval`（`lx_bridge.html:834`），能直接访问闭包变量 | `JS_Eval` 默认在全局作用域，闭包变量访问不到 |
| 换脚本 | `controller.refresh()` 换整个 realm，天然干净 | 同一个 `JSContext` 反复 eval，脚本顶层 `const` 会 **redeclaration 报错** |

**结论：每个 LX 脚本新建一个 `JSContext`**（`JS_NewContext` 几毫秒，可接受）。这样代际隔离、全局污染、`const` 冲突、dispose 全部天然解决，比在同一个 context 里做清理可靠得多。runtime 可以复用一个。

**关键决策：抽公共核**

`LXSourceEngine.ets` 有 790 行，其中与"传输层"无关的是：请求队列、超时、看门狗、更新检查拦截、代际校验、日志。这些必须抽到 `LxEngineCore.ets`，两种引擎共用。**不要复制粘贴**，否则今后改一处要改两处，这就是当前仓库最大的技术债来源。

**验收**

- 6 个平台（kw/kg/tx/wy/mg/qs）各有至少 1 个脚本，能完成：`init` 成功 → `search` → `musicUrl` → `lyric`。
- `lx.utils.crypto.md5` / `randomBytes` / `zlib.inflate` 各跑一次单测通过；`aesEncrypt` / `rsaEncrypt` 至少有一个真实脚本验证通过（用汽水源试）。
- 换脚本连续 10 次（不同脚本），无 `redeclaration` 报错、无内存增长。
- ArkTS 侧日志与 WebView 版逐条对齐（同样的 `appendPlayLog` 文案）。
- 注入耗时：从"注入分片数=114"变成单次 eval，日志打 `evalMs`。

## 6. 风险清单

| 风险 | 概率 | 影响 | 处置 |
|---|---|---|---|
| 第三方脚本用了 DOM | 高（必然存在） | 若误判进 QuickJS 直接 `ReferenceError` | **不靠运行时给空壳**（空壳＝假装能用，更难查）：probeScript 前置判到 WebView；运行时再兜一次，失败自动切 WebView 重试 |
| **QuickJS 收益未验证** | **中** | 白做 1~2 周 | Phase 0 先测 A/B/C 三基线；Phase 4 决策表 < 30MB 就砍掉整条线 |
| 真实脚本 DOM 依赖比例过高 | 中 | QuickJS 只能接管少数脚本，成本摊不平 | Phase 0 把每个脚本的 `probeScript` 结果打日志；> 50% 判到 WebView 就砍 |
| **加密/压缩能力补不齐**（AES / RSA-OAEP / deflate） | **高** | **部分平台取址直接失败**（汽水、部分元力源用 aes 签名） | 先做 `randomBytes + zlib`，aes/rsa 抛可捕获错误并**自动切 WebView 模式重试一次** |
| QuickJS 内存爆（脚本缓存大 JSON） | 中 | 进程被杀 | 256MB 上限 + OOM 时自动切 WebView 重试一次 |
| native 线程死锁 | 中 | 卡死 | 所有跨线程调用带超时；压测必须过 |
| `JS_Eval` 大脚本卡主线程 | 低 | 首帧卡 | eval 放专属线程，不占 ArkTS 线程 |
| quickjs-ng API 与文档不符 | 中 | 编译失败 | 锁版本 tag，不要跟 master |
| `libc++_shared.so` 冲突 | 高 | 安装失败 | 与 mpv 共用同一份，CMake 里只 link 不重新编 |
| 顶层 `const` 重复声明 | 高（若共享 context） | 换脚本时 `SyntaxError` | **共享 runtime + 每脚本新建 context**（几十 KB，可忽略）。这不是「强制约束」，是 QuickJS 的语义要求，成本几乎为零 |

## 10. 给接手 Agent 的最后提醒

- 本仓库**没有 git**，动手前第一件事是 `git init` 并提交基线，否则你改坏了没法退。
- 本仓库的注释**不能全信**：至少 `AudioKernel.ets`、`KernelFactory.ets`、`UsbAudioService.ets` 三处的头注释与实现相反。判断以代码为准。
- 三个大文件里的中文是**乱码**（`PlayerExpandState` / `PlaybackPage` / `Index`），不要试图理解，也不要基于它们做设计。
- 遇到"注释说 A、代码做 B"时，**以代码为准，并把注释改成 B**——这是本仓库最需要养成的习惯。
