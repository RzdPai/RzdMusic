## 0. 先说一个**方向搞反**的坑（必读）

上一轮（§26 那一批）我们按"内容不许画进状态栏"去改，给**内容容器**加了
`.padding({ top: 状态栏高度 })`。用户澄清后才知道方向反了：

> **页面要"延伸进状态栏"** —— 列表往上滚要能一直画到屏幕最顶端，状态栏那一条也归页面（沉浸式）。

而且这里还有个**前提被判反了**：§26.2 曾写"`NavDestination` 内容区默认就在状态栏下沿起排"，
实际**相反** —— 壳层 `products/default/src/main/ets/pages/Index.ets` 的 `HdsNavigation` 自带
`.ignoreLayoutSafeArea([...],[TOP,BOTTOM])`，而 `expandSafeArea` 只扩绘制区 ⇒
**二级页内容区是从屏幕 y=0 起排的**。所以：

| 做法 | 结果 |
| --- | --- |
| 把状态栏高度加到**内容容器的 padding** 上 | 滚动视口从状态栏下沿起排 ⇒ 状态栏那一条永远是死背景 ✗（用户说的"不会延伸"） |
| 把"**状态栏 + 标题栏**"（38 + 56 = 94）放进**滚动内容里**（`contentStartOffset` / 滚动内容首项一个 `Blank()`） | 静止时第一行正好落在标题栏下沿；往上滚则整行从标题栏底下**穿进状态栏** ✔✔ |

**本轮统一口径**：有 HDS 标题栏的二级页 = 容器**不加**顶部 padding + 偏移放**滚动内容里**（=94vp）。
`hideTitleBar(true)` 的手表向页 = 容器让开状态栏即可（它们没有标题栏，也没有"穿进状态栏"的要求）。

## 2. 状态栏延伸（本条是本轮的主改）—— **官方正解：`clipContent(ContentClipMode.SAFE_AREA)`**

用户口径（两次纠正后）：**页面要"延伸进状态栏"** —— 内容（列表）往上滚要能一直画到屏幕最顶端。

**官方《开发应用沉浸式效果》给出的答案**（原文）：

> 「**组件安全区方案**：布局系统保持安全区内布局，然后通过接口延伸**绘制**内容（如背景色，背景图）到状态栏和导航区域……
> 该方案下，**界面元素仅做绘制延伸，无法单独布局到状态栏和导航区域**……」
> 「**滚动类场景**：滚动容器设置 `expandSafeArea` 属性生效，但当**父组件是滚动容器**时，子组件设置 `expandSafeArea`
> **不生效**。对于滚动容器的子组件，有两种方法实现沉浸式效果：
> ① 设置父组件滚动容器和子组件相同的背景色，给父组件设置 `expandSafeArea`；
> ② ……设置滚动容器的内容裁剪属性 **`clipContent(ContentClipMode.SAFE_AREA)`**，**将内容层裁剪区域扩展至避让区**。」
> 另（`expandSafeArea` 原理）：「……**需要确保父组件未设置 clip 等裁剪属性**。」

⇒ **真正的病根**：滚动容器（`List`/`Scroll`）默认按**安全区**裁剪内容，
所以无论我们把"状态栏 + 标题栏"的偏移放在容器上还是内容里，**行滚到状态栏那一条都会被裁掉**。
个别页面上还写着 `.clip(true)`（裁到 padding 内侧的内容矩形），更是雪上加霜。

**改法（每页两条）**：
1. 给该页的滚动容器加 **`.clipContent(ContentClipMode.SAFE_AREA)`**（`ContentClipMode` 是全局枚举，@since 14，
   本工程 compatible 6.1.1(24) 可用，**不需要 import**）；
2. 保证"页根 → 容器 → 滚动容器"这条链上**任何一层都没有 `clip(true)`**（上一轮我在几页容器上加过的 `.clip(true)` 已删）。

**保留**上一轮定的"状态栏 + 标题栏"（≈94vp）偏移仍在**滚动内容里**（`contentStartOffset` / 内容首项 `Blank()`）——
它保证静止时第一行落在标题栏下沿；`clipContent(SAFE_AREA)` 保证上滑时行能画进状态栏。

**落点**：
* 本页自己改的：`RecordListPage`（`List` 的 `.clip(true)` → `.clipContent(SAFE_AREA)`）、
  `SettingsDetailPage`（7 个面板 `Scroll` 各加一句 `clipContent(SAFE_AREA)`）。
* 扫尾（同一规则）：全部歌单 / 歌单首页（两支 List）/ 听歌识曲 / 在线搜索 / 设置 / 同步设置（面板内 `Scroll`）。
* **不适用**：整页一张大图的 `PlaylistDetailPage` / `ArtistDetailPage` / `AlbumDetailPage`（状态栏那一条本来就是照片，
  照片层自己已有 `ignoreLayoutSafeArea(TOP)`）；`CloudMusicPage`（公式本来就对）；
  手表向的 `PlaylistHubPage` / `SongQueueListPage` / 自绘固定头的 `LocalMusicView`。

**窗口侧的事实（顺带查过）**：本工程只在播放页那一段调 `setWindowLayoutFullScreen`
（`WindowUtil.setFullScreen` 只被 `applyPlaybackWindowChrome` 调用），平时窗口**不是**全屏布局 ⇒
按官方口径属于"组件安全区方案"，所以**只能靠绘制延伸**（`expandSafeArea` / `clipContent(SAFE_AREA)`），
这也正是上面这套改法的适用场景。

## 3. 平台音乐页面没模糊效果 —— 根因：**滚动容器没接上标题栏**

HDS 标题栏的"滑过才渐变模糊"是**绑定驱动**的：页根 `.bindToScrollable([this.pageScroller])`。
`SettingsDetailPage` 渲染平台音乐时写的是 `PlatformMusicPage({ onClose })` —— **没把 `pageScroller` 传下去**，
子页就用它 `@Param pageScroller = new Scroller()` 的**默认值**去包 `Scroll` ⇒ 它滚它的、
标题栏收不到滚动量 ⇒ **材质在、但永远不模糊**。

**同一个 bug 还有一处**：`DownloadManagerSection()`（设置页与设置详情页两处调用）也没传 scroller。
两处都已接上（平台音乐那处顺带补了 `contentTopOffset: this.contentTopOffset()`）。

**排查口径**：先查 scroller 是不是同一个实例，再怀疑材质/参数 ——
`enableScrollEffect` 官方默认就是 `true`、`blurEffectiveEndOffset` 默认 `vp(8)`，
"少写这两个"**不是**不模糊的原因。

## 4. 用户第三次纠正：**标题栏位置** + **底部留白的落点**（定稿）

> 用户（附「我的收藏」截图）：「现在**很多页面是整个标题移到了状态栏下面**，不过设置里的二级界面都正常了
> （包括音源管理），但是**上方留的空距有点大了**。音源管理页面底部还是空白，我感觉是**你又把底部留白写死在
> 屏幕底部而不是列表底部**了（你经常犯这个毛病）」

### 4.1 标题栏掉下去一截 = **让了两次状态栏**

按截图量：标题栏落在 ≈76..132，正确位置是 38..94 ⇒ 差**一个状态栏高度**。
原因：**HDS 标题栏自己会按状态栏高度往下让位**，而二级页的**页面盒子又已经让开了状态栏** ——
因为 `ignoreLayoutSafeArea` 是**逐组件生效**的（官方「子节点可以单独设置该属性」），
壳层 `HdsNavigation` 上那个 TOP **不会传染**给被推入的 `NavDestination`。

**★ 本仓自己就有一个对照样本**：一级页「我的」（`MinePage`）**本来就写着**
`.ignoreLayoutSafeArea([SYSTEM], [TOP, BOTTOM])` —— 它的标题栏位置一直是对的（用户从没抱怨过这一页），
而所有"只写 BOTTOM"的二级页标题都掉了一截 ⇒ 两边一比，口径就定了 ✔。

**定稿口径（状态栏三件套，缺一不可）**：
1. 页根 `HdsNavDestination`：`.expandSafeArea([SYSTEM], [TOP, BOTTOM])`（底色铺到两条避让区，只扩绘制）；
2. **`.ignoreLayoutSafeArea([SYSTEM], [TOP, BOTTOM])` —— TOP 必须给**（盒子从屏幕 y=0 起排，
   HDS 标题栏自己那一次让位正好落在 38..94）；
   ⚠️ 之前那句"根节点带 TOP 会把标题顶进状态栏、只能留 BOTTOM"**是错的**（上一轮的猜测，已被用户现场否掉）；
3. 滚动容器 `.clipContent(ContentClipMode.SAFE_AREA)`（让行能**画进**状态栏）；
4. 首项之前的留白 = **状态栏 + 标题栏（≈94）**，写在**滚动内容里**（`contentStartOffset` / 首项 `Blank()`）。
   ⇒ 盒子从 0 起排后：标题栏 38..94 ✔、首项 94 ✔（原来首项落在 132 = 盒子 38 + 94，就是"上方空距有点大"）。

### 4.2 底部留白**必须跟着内容滚**（"写死在屏幕底部"是我的老毛病）

「音源管理页面底部还是空白」的原因：留给悬浮播放条的 88vp 写在了**最外层容器**
`padding({ bottom: SETTINGS_PANEL_BOTTOM_VP })` 上 —— 那是**固定在屏幕底部的一条死带**，
列表永远用不到它，滚到底就露一块空白 ✗。

**定稿口径**：底部留白写成**滚动容器**的 **`.contentEndOffset(<留白>)`**
（`ScrollableCommonMethod`，@since 22，List/Scroll 通用；语义 = "内容末端到显示区边界的距离"，随内容滚走），
或滚动内容**末尾**的一个 `Blank()`。本轮已把音源管理面板改成 `contentEndOffset(SETTINGS_PANEL_BOTTOM_VP)`
并去掉外层 `bottom` padding。

（其余 5 个设置面板的 `bottom: SETTINGS_PANEL_BOTTOM_VP` 本来就落在**滚动内容根 Column** 上 ⇒ 会跟着滚 ✔ 不用改；
`OnlineImportSheet` 那种不滚动的短表单留外层 padding 也可以。）

## 6. 第四轮：真正的根因 —— 避让区是 0（"时好时坏"的来源）

用户 21:04/21:05 的真机截图把范围压到了三件事：设置页首页 / 历史页 / 收藏页**标题下移**、
平台音乐页**上方内容没延伸**、二级页**底部播放器明显错位**，外加一个手势问题
（我的页从播放器上面一段上滑也打开播放器）。

### 6.1 根因（源码级确证，不是猜）

`common/musicbasic/src/main/ets/util/WindowUtil.ets`：

| 事实 | 位置 | 后果 |
| --- | --- | --- |
| 避让区读不到时 `statusBarTopVp = 0` | 旧 `syncWindowInsetsVp()`（`ctx === undefined` 分支、`avoidSystem === undefined` 分支各写一次 0） | 页顶让位从 `38 + 56` 静默变成 `56` |
| `syncWindowInsetsVp()` **只在** `onAvoidAreaChange` 里被调（外加 `updateWindowInfo()` 一次） | `onAvoidAreaChange` → `syncWindowInsetsVp()` | 状态栏高度不变 ⇒ **不再有任何回调** ⇒ 那个 0 **永久留下** |
| 专门留的"启动快照" `getStartupStatusBarTopVp()` / `getStartupNavigationBarBottomVp()` **全仓无人调用** | 全仓 grep | 兜底机制写了却没接上 |
| 消费方直接读 `mainWindowInfo.statusBarTopVp` | `getStatusBarTopVpFromWindowUtil()` | 拿到的就是那个 0 |

为什么表现成"**有的页面好、有的页面坏**"：页面的让位值是在**它自己的 build 里**算的，
谁在避让区到齐**之前**首帧、之后又没有 `@Trace` 变化触发重绘，谁就定格在 0（少让 38vp ⇒
内容顶进 HDS 标题栏 ⇒ 看着像"标题下移/被内容压住"）；恰好在值到齐之后才首帧的页面就是对的。

### 6.2 改法（`WindowUtil` + `StatusBarInsetUtil`）

1. **只读解析器**（可安全在 `build()` 里调用，不写状态、不会造成重绘循环）：
   `resolveStatusBarTopVp()` / `resolveNavigationBarBottomVp()`，取值顺序
   **缓存 → 现向窗口量（`getWindowAvoidArea`）→ 最后一次量到的好值 → 启动快照**。
2. `syncWindowInsetsVp()` **不再把好值覆盖成 0**：量不到就保留 `lastGood*`；
   同时补上"绕过缓存直接向窗口量"的一次读数（`readStraightStatusBarTopVp()` /
   `readStraightNavigationBarBottomVp()`）。
3. `px2vpSafe()`：`UIContext` 还没 cache 时用 `display.getDefaultDisplaySync().densityPixels` 换算，
   不再因为"ctx 没有"就整条腿断掉。
4. `getStatusBarTopVpFromWindowUtil()` 改为走解析器 ⇒ **全仓 20+ 个消费点一处生效**，
   新增 `getNavigationBarBottomVpFromWindowUtil()`（同样语义）并在 `musicbasic/Index.ets` 导出。
5. 壳层浮动条底部边距 `floatingMiniBarBottomMarginVp()` 改用新解析器 ——
   原来只读"缓存 + 启动快照"，两者都为 0 时边距退化成 12，胶囊贴屏幕底压在系统手势条上，
   就是用户说的「二级页底部播放器明显错位」。
6. 日志标签 **`RzdWindowInsets`**（`grep RzdWindowInsets`）：每次同步都打印
   `statusBarTopVp / navBarBottomVp / avoidSystemVp / straightStatusVp / avoidNavVp / straightNavVp`，
   下面这轮真机一眼就能看出是"缓存 0 但直读有值"还是"系统真的没给"。

### 6.3 上拉打开播放器：把热区收紧成"迷你条那一条"

旧规则 `fingers[0].globalY >= 0.6 * 屏高` ⇒ **整个下半屏**都是拉伸手势热区。
别的页面那一带正好是长列表，竖直拖动被列表先吃掉（壳层 `.gesture(PanGesture)` 在冒泡阶段，
优先级低于子组件）⇒ 只有内容不满一屏 / 已滚到底的**「我的」页**会漏给壳层，
于是"从播放器上面一部分上滑也打开播放器"。

现在：起手点必须落在**贴底那一条带** `PULL_OPEN_HANDLE_BAND_VP = 112`
（迷你条 56 + 底部避让 14~24 + 8 边距 + 上沿余量）内 —— 迷你条就是那个把手，
页面中段/列表区域的上滑一律交还滚动视图。

### 6.4 本轮**没有**动的东西（下一轮的一个变量）

`avoidLayoutSafeArea: true` 保持不动。参考工程 `lxmusic-harmony` 对它的注释是
「让返回键与标题自己退到状态栏下方」（= HDS 标题栏自己加状态栏内边距），
内容层再按 `标题栏高度 + 状态栏高度` 让位 —— 我们和它**逐字同构**，所以先修避让区那个 0。
若打完包标题仍然偏低，下一轮的**单个变量**就是把这几页的 `avoidLayoutSafeArea` 改成 `false`
（标题栏不再自己下移，配合内容层 94 的让位）。
